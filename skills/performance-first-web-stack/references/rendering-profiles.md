# Alternative rendering profiles

Use when selecting or implementing Marko, Leptos, or server templates with HTMX. Apply the [core policy](../AGENTS.md), [architecture criteria](architecture.md), and shared [frontend requirements](frontend.md). Read only the selected section. These choices replace overlapping Solid-specific libraries at the affected UI boundary; Rust retains domain/data/resource authorization.

## Marko: streaming and resumable web tier

Recommend [Marko 6](https://markojs.com/docs/introduction/welcome-to-marko) when streaming dynamic HTML, reducing browser startup work, and fine-grained updates fit the product and its component needs. Keep SolidStart as the general interactive default and Astro for mostly static content.

- Use supported Marko Run/Vite routing and rendering with compatible pinned Marko, Marko Run, Vite, and adapter releases. Use the Marko 6 Tags API rather than copying Marko 5 Class API recipes. Verify actual Bun execution or the selected Workers adapter and streaming through the production proxy/CDN; package installation alone proves neither.
- Keep domain operations in Rust. Marko may coordinate SSR data under the existing [BFF criteria](architecture.md); do not introduce a redundant forwarding service. Reuse the Rust API contract and verify identity across that boundary. Authorize before streaming private HTML and serialize only intended browser-visible state.
- Check `.marko` files with [`@marko/type-check`](https://markojs.com/docs/reference/typescript), retaining official TypeScript checks for other entry points; `tsc`/tsrs alone do not cover templates. Use scoped [Prettier with `prettier-plugin-marko`](https://markojs.com/docs/introduction/integrations) where Oxlint/Oxfmt lack coverage, with one formatter per file. Configure actual template/route entry points and use `@marko/testing-library` for applicable component behavior.
- Use Marko's own reactivity and compatible UI. Solid primitives, hooks, Unpic components, and StyleX's Solid integration do not transfer automatically. Prefer native CSS/responsive images or verified integrations without adding Solid solely for a library. Test loading/error boundaries, resumability, and forms; measure complete routes rather than assuming resumability wins every workload.

## Leptos: Rust-rendered UI and interactive WASM

Recommend [Leptos](https://book.leptos.dev/ssr/index.html) when Rust throughout the UI/server boundary and compatible UI integrations benefit the project. Use its supported Axum integration for SSR/streaming and Rust domain calls in the same process where appropriate. This profile can replace the separate SolidStart/Bun SSR tier; an extra JavaScript server is unnecessary solely for rendering.

- Pin compatible Leptos, Axum integration, `cargo-leptos`, and Rust toolchain versions using matching release documentation. Prefer a supported non-prerelease combination; review pre-1.0 minor changes and any selected experimental features. Install only the needed native and WASM targets/tools.
- Render suitable routes on the server and select full hydration or [islands](https://book.leptos.dev/islands.html) deliberately. Interactive browser code ships as WASM with JavaScript glue; Rust is not automatically lighter than Solid. Inspect compressed WASM/JS, startup, hydration, and interaction costs using a release build and the [binary-size guidance](https://book.leptos.dev/deployment/binary_size.html).
- Keep SQLx, secrets, provider SDKs, and authoritative domain logic in the server build. Treat [server functions](https://book.leptos.dev/server/25_server_functions.html) as public request entry points: validate inputs, authenticate, authorize resources, and protect cookie-authenticated writes. Compiler feature separation and typed calls are not authorization. Avoid serializing secrets in rendered state.
- Use Leptos signals/resources, compatible Rust UI, and native forms/progressive enhancement where supported. Solid components, Valibot browser schemas, and StyleX integrations are not requirements for this profile. Call domain code directly during SSR; Leptos server functions can serve first-party interactions without a duplicate JSON API. Retain OpenAPI for public/polyglot consumers sharing the same domain behavior.
- Use the release's `cargo-leptos` workflow to build/check native SSR and WASM hydration configurations separately; do not blindly combine mutually exclusive features. Retain rustfmt, Clippy, server tests, and browser journeys, including direct navigation, hydration, validation, and failure states. JavaScript tooling applies only to actual JS/TS assets or tooling. Bound compile concurrency and caches.

## HTMX: Rust-rendered pages and fragments

Recommend [HTMX](https://htmx.org/docs/) with Axum and an escaping server-template renderer for forms, search, pagination, and similar server-owned interactions. Rust can serve pages, fragments, and domain operations together. Keep SolidStart for extensive local/offline interaction when its client model better fits.

- Use HTML responses for UI updates and direct Rust domain calls behind the handlers; add no Bun tier or JSON proxy solely for this profile. Keep JSON/OpenAPI for public/polyglot clients. Preserve full-page URLs and native form actions/methods where possible, with the same validation and resource authorization on every endpoint. `HX-*` headers are request hints, never identity.
- Escape untrusted content and protect cookie-authenticated mutations against CSRF. Use supported HTMX history controls to exclude sensitive pages from browser snapshots, and retain private/shared-cache isolation.
- If a URL returns full pages or fragments based on `HX-Request`, send `Vary: HX-Request`, distinguish cache validators/variants, and request full documents during history restoration (`historyRestoreAsHxRequest: false` where supported). Separate fragment URLs also work. Verify direct visits, refresh, and Back/Forward behavior.
- Configure validation/error statuses and swap behavior, expired sessions, retained input, pending submissions, and stale responses. Test keyboard/focus and announcements after swaps; separate DOM ownership from any client-framework widgets. Pin HTMX and required extensions, and compare HTML bytes, round trips, server load, and interaction latency under the [measurement policy](performance.md).
